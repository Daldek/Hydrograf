## Own data and new sources (extensions of the browsing mode)

Vision (brainstorm 2026-07-31, full reasons: `notes/plans/2026-07-31-wlasne-dane-i-nowe-zrodla-wizja.md`): the core stays the browsing mode — an automatic analysis from public data. Uploading own data is an optional extension for project uses where public data is not enough (Kamil's feedback: urban watersheds, the sewer, HSG).

- [ ] The analysis extent from a vector file in the admin panel (instead of drawing a rectangle). Why: real projects have irregular boundaries; a rectangle forces processing of surplus data.
- [ ] Clipping the result data to the analysis area. Why: results beyond the area boundary are noise and a false context; a natural consequence of the vector extent.
- [ ] The aPGW catchments as a data source + choosing the analysis area by a catchment ID. Why: the official hydrographic division as a reference and a fast definition of an area without drawing.
- [ ] Uploading an own DEM instead of downloading it from the geoportal. Why: projects have a more accurate/up-to-date survey (a flight, LiDAR); independence from the availability of the geoportal.
- [ ] Uploading an own streams layer (moved out of the entry about the YAML file). Why: BDOT10k is sometimes incomplete; an uploaded layer becomes the basis of the river network parameters (cf. the morphometry entry).
- [ ] Uploading own soil data. Why: projects have soil surveys more accurate than the HSG (cf. the HSG entry).
- [ ] Uploading own land use. Why: the design state (e.g. planned development) instead of the current state from public data.
- [ ] IMGW river gauges (through IMGWTools): a layer of the locations + readings (levels/flows); in the end a verification of the computed flows with observations. Why: validation of the model in watersheds closed by a gauge.
- [ ] PMAXTP (through IMGWTools): downloading the maximum precipitation of a given probability for a chosen point. Why: the design precipitation for the design hyetograph/hydrograph.
- [ ] Export of the data of a selected area from the GUI (DEM, flow lines, depressions, results of the analyses — GeoTIFF/GeoJSON/GPKG). Why: the results must reach further design tools (QGIS, sewer models). Note: this means a file export, NOT running the pipeline from the GUI (clarified in the brainstorm).
- [ ] Attaching own WMS services as a base layer (client-side handling). Why: users have sector WMS services (sewer, local spatial plans); client-side = zero load on the backend.
- [ ] Hints and explanations of the parameters and indices in "Parametry zlewni" (watershed parameters): tooltips/an "i" icon at the items. Why: a lower entry threshold — interpreting the results without expert knowledge.

- [ ] **An ADR to decide — versioning of the DEM sheets** (session 93). The problem: GUGiK publishes the DEM in layers by the year of currency (`SkorowidzeNMT2025`/`2024`/`2023`/`2022iStarsze`), while on the Hydrograf side a file = only the path from the sheet code — the year is lost, `skip_existing` blocks updates, the mosaic mixes flights of different years without a trace (elevation steps at the joins are possible, changes of a watershed between bootstraps that cannot be explained). The proposed solution:
  1. The layout of the files unchanged (one, the newest known version per sheet code, the paths of Kartograf) + a manifest in `<HOST_DATA_DIR>/nmt/` (SQLite/GPKG) with the full record of the index: sheet code, `aktualnosc`, `numerZgloszeniaPracy`, `zrDanych`, `bladSredniWysokosci`, `dt_pzgik`, the OpenData URL, the download time (timestamp, required), sha256. The version key: `numerZgloszeniaPracy` + `aktualnosc`. `zrDanych` matters hydrologically (photogrammetry vs lidar — a different quality at the same mean error). Rejected: directories per year (`nmt_5m/2025/...`) — they break `skip_existing`, duplicate the data, and the mosaic needs a choice of "the newest per sheet" anyway.
  2. An update = a diff of the index against the manifest: a WMS query without downloading files, downloading again only the sheets with a changed URL; the previous version is moved to `archive/`.
  3. Provenance in the bootstrap: the list of the sheet versions (or the hash of the manifest) saved in the metadata of the run in the DB; optionally a layer "year of the flight per sheet" to diagnose the joins.
  - **Decided (user, s93):** the old versions are archived, not overwritten. The layout of the archive: a common directory `archive/` in `<HOST_DATA_DIR>/nmt/` with a subdirectory per product (a counterpart of the current one, e.g. `archive/nmt_5m`, `archive/nmt_1m`, others as needed), then the hierarchy of the sheet code as in the current data, the year of currency (of the flight) as a prefix of the name separated by `_`: `archive/nmt_5m/<sheet code hierarchy>/<aktualnoscRok>_<sheet code>.asc`, e.g. `archive/nmt_5m/M-33/48/D/d/3/1/2019_M-33-48-D-d-3-1.asc`. The year comes from the field `aktualnoscRok` of the index record (the state of the terrain), not from `dt_pzgik` (publication) nor from the layer name (`2022iStarsze` is a grouping). **No collision suffix** — the user accepts the risk that two versions of a sheet from the same year (e.g. a correction of the same flight) will take the same name and the later archived one will overwrite the earlier; the full identification of a version is only in the manifest (`numerZgloszeniaPracy`, `aktualnosc`, `dt_pzgik` + the download time). Rejected: directories per year — the state "as of the day of the bootstrap" mixes the years, so it is reproduced from the manifest.
  - The source of the metadata: Kartograf. Since ADR-061 its store keeps every flight of a sheet as a version under `versions/`, with a sidecar that records the campaign (`id`, `date`), the acquisition date, the OpenData URL and the `sha256`, and the standard path is a hard link to the newest flight; that covers the version key and the kept old versions of points 1 and 2 in part. Still to decide: the provenance of a bootstrap (point 3) and whether Hydrograf keeps an archive of its own. The first manifest: Opolskie, together with the verification of the 92 sheets downloaded after the error of the 2025 layer.
  - The ADR number is given at acceptance (the next free one: 062). Priority: medium, before downloading the whole of Poland.
